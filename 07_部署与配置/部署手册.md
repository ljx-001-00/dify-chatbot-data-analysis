## 1. 智能中枢 P2：基础服务

### 1.1 关闭 firewalld（重要）

```bash
systemctl disable --now firewalld
```

> 原因：`firewall-cmd --reload` 会重建 iptables 链，把 Docker 自己的 `DOCKER-ISOLATION-STAGE-1` 等链接删掉，表现为「容器在跑、端口映射却连不上」。若必须保留防火墙，改用 `iptables` 持久化规则，不要用 firewalld 管 Docker 端口。

清空残留规则（执行过一次即可）：

```bash
iptables -F DOCKER-ISOLATION-STAGE-1 2>/dev/null
systemctl restart docker
```

### 1.2 MySQL 8.0

```bash
docker run -d --name mysql8 --restart unless-stopped \
  -p 3306:3306 -e MYSQL_ROOT_PASSWORD=<MYSQL_PASSWORD> \
  -v /home/data/mysql:/var/lib/mysql mysql:8.0
```

建库建表：

```sql
CREATE DATABASE IF NOT EXISTS wechat DEFAULT CHARSET utf8mb4;
CREATE DATABASE IF NOT EXISTS chat   DEFAULT CHARSET utf8mb4;

USE wechat;
CREATE TABLE chathistory (
  chathistoryid INT AUTO_INCREMENT PRIMARY KEY,
  user_input    TEXT,
  response      TEXT,
  create_time   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE new_chathistory (
  id      INT PRIMARY KEY,
  time    DATETIME,
  records TEXT
);
```

> 注意：`create_time` 必须给默认值，否则从 `chat.records` 灌数据时会报 `ERROR 1138 Invalid use of NULL value`。主键名是 `chathistoryid`，不是 `id`。

### 1.3 Xinference（CPU 推理）

镜像：`xprobe/xinference:v1.17.1-cpu`（离线包 3.12 GB，`docker load -i` 导入）。

```bash
docker run -d --name xinference_container \
  --network host --restart unless-stopped --shm-size=4g \
  -e XINFERENCE_CORS_ALLOW_ORIGINS='*' \
  -e XINFERENCE_HOME=/data \
  -e XINFERENCE_MODEL_SRC=modelscope \
  -e XINFERENCE_HEALTH_CHECK_FAILURE_THRESHOLD=60 \
  -e XINFERENCE_HEALTH_CHECK_INTERVAL=5 \
  -e XINFERENCE_HEALTH_CHECK_TIMEOUT=120 \
  -v /home/data:/data \
  xprobe/xinference:v1.17.1-cpu xinference-local -H 0.0.0.0
```

启动耗时约 60 秒，出现 `Uvicorn running on http://0.0.0.0:9997` 即成功。

**三个参数为什么必须改**：容器内 `xinference/deploy/local.py` 先 `poll(timeout=10)` 等父进程，再用「5 次 × 5 秒 = 25 秒」窗口做健康检查。而冷启动要 33~44 秒（import torch / transformers / pandas 全栈），窗口永远差 8 秒，于是每次都误报 `Cluster is not available after multiple attempts`。放大到 `60 次 × 5 秒`、单次超时 120 秒后一次通过，**无需改镜像**。

**`--shm-size=4g` 为什么必须加**：Docker 默认 `/dev/shm` 只有 64 MB，supervisor 子进程申请共享内存失败会直接退出，表现为容器启动后秒退、`docker logs` 只有一行。

### 1.4 加载本地 GGUF 模型

把两个 GGUF 放到 `/home/data/models/`（`chown -R 1000:1000` 保持容器内用户可读），然后：

```bash
cat > /tmp/qwen.json <<'EOF'
{
  "model_name": "qwen2.5-instruct",
  "model_engine": "llama.cpp",
  "model_format": "ggufv2",
  "model_size_in_billions": "1_5",
  "quantization": "q4_k_m",
  "model_path": "/data/models/qwen2.5-1.5b-instruct-q4_k_m.gguf",
  "model_uid": "qwen2.5-instruct",
  "n_gpu": "auto",
  "n_ctx": 4096
}
EOF
curl -s -X POST http://127.0.0.1:9997/v1/models -H 'Content-Type: application/json' -d @/tmp/qwen.json
```

- `model_size_in_billions` 必须是字符串 `"1_5"`，写 `1.5` 会报 `Model not found ... size: 1.5`。
- `n_gpu` 只能是 `"auto"`，该版本不接受 `"none"`。
- 重复提交同一 `model_uid` 会报 `Model is already in the model list`，先 `curl -X DELETE .../v1/models/<uid>` 再重试。
- 加载约 60 秒，`/v1/models` 里的字段是 `id`，不是 `model_uid`。

DeepSeek-R1-Distill-Qwen 同理，改 `model_name`（`deepseek-r1-distill-qwen`）、`model_path`、`model_uid`，量化名大写 `Q4_K_M` 只是文件名习惯，请求里仍写小写 `q4_k_m`。

## 2. 业务主机 P1：微信回调与 MCP

### 2.1 MCP 数据库服务

```powershell
cd C:\Users\HP\Documents\deepseek-harness\default-workspace\mysql_mcp
python -m venv .venv
.\.venv\Scripts\activate
pip install pymysql -i https://mirrors.aliyun.com/pypi/simple/ --timeout 15 --retries 3
$env:MYSQL_PASSWORD="<MYSQL_PASSWORD>"; $env:MYSQL_DB="wechat"
python mysql_server_nodep.py     # 监听 0.0.0.0:8095，健康检查 /health
```

> 该服务用标准库 `http.server` 手写 MCP 协议，**不依赖 fastmcp**（装 fastmcp 会卡在几十个间接依赖上）。
> 协议要点：对 `notifications/*` 必须返回 **202 空响应**，返回 204 会让 Dify 报 `Invalid JSON: EOF while parsing a value`。

在 Dify 里注册：工具 → MCP → 添加服务（HTTP）
- 服务端点 URL：`http://192.168.1.11:8095/mcp`
- 名称：`database_tool`，标识符：`database_server`，超时 30，SSE 读取超时 300

### 2.2 微信回调服务

```powershell
cd C:\Users\HP\Documents\deepseek-harness\default-workspace
python -m venv .venv
.\.venv\Scripts\activate
pip install flask wechatpy requests pymysql -i https://mirrors.aliyun.com/pypi/simple/
python wechat_public_bot.py       # 监听 0.0.0.0:80
```

`wechat_public_bot.py` 顶部配置区需填写：

```python
APP_ID            = '<YOUR_APP_ID>'
APP_SECRET        = '***'
TOKEN             = '<YOUR_VERIFY_TOKEN>'
ENCODING_AES_KEY  = '<YOUR_AES_KEY>'   # 43 位
DIFY_API_KEY      = 'app-***'
DIFY_WORKFLOW_URL = 'http://192.168.1.10/v1/workflows/run'
DIFY_TIMEOUT      = (1.5, 4.8)     # 连接 1.5s / 读取 4.8s，微信硬超时 5s
```

关键实现（答辩会问）：
- **安全模式**：`encrypt_type == 'aes'` 时用 `WeChatCrypto(TOKEN, AES_KEY, APP_ID).decrypt_message(...)` 解密，回复时同样加密。密钥必须是 43 位，`assert len(self.key) == 32` 报错就是这里长度不对。
- **预热线程**：启动时先打一次 Dify，把 worker 冷启动（首次 20.7 s）挪到服务启动阶段。
- **落库异步**：回复先返回，`save_history()` 在后台线程直连 MySQL 写入，避免 Dify 调 MCP 的 4.5 秒尖峰拖垮 5 秒预算。
- **敏感词拦截**：辱骂类先拦截并返回统一话术，不进模型。

## 5. 常见故障速查

| 现象 | 判断依据 | 处置 |
|---|---|---|
| `Cluster is not available after multiple attempts` | 日志末尾没有 `Uvicorn running` | 提高三个健康检查环境变量（见 1.3） |
| 容器起来几秒就退出 | `docker inspect` 显示 `ExitCode=1`、`OOMKilled=false` | 补 `--shm-size=4g` |
| 宿主 curl 000、容器内 200 | `docker port` 有映射但连不上 | `systemctl restart docker` 重建 iptables 链 |
| Dify 页面打不开 | `firewall-cmd --reload` 之后出现 | 停用 firewalld，不要用它管 Docker |
| 微信收不到消息 | 日志完全不增长 | 查 frpc 是否在跑、后台「消息推送」是否被停用 |
| 回复「网络服务有点忙」 | 日志出现 `Dify 超时（>4.8s）` | 看 Dify 追踪页哪个节点慢，通常是 LLM |
| 解密失败 `utf-8 codec can't decode` | 签名正确但解密报错 | AESKey 与后台不一致，或加解密方式不是安全模式 |
| MCP 报 `Invalid JSON: EOF` | Dify 添加 MCP 服务时报 | 服务端对通知请求返回 202 而非 204 |

## 6. 商品价格表（价格类问题的结构化查询）

RAG 只能看到 TopK 局部段落，做不了「最贵是哪款」这种全局排序，模型会随机挑数字。
因此价格、排名、型号参数统一走 MySQL。

```bash
# 建表 + 灌入示例数据
mysql -uroot -proot wechat < products.sql
# 或：用真实价目表覆盖（CSV 支持中文表头，价格填整数）
python init_products.py 价目表.csv
```

CSV 表头（任选一套）：

```
model,category,capacity_l,price,energy,warranty,stock,features
型号,类型,容量,价格,能效,保修,库存,卖点
```

验证：

```sql
SELECT model, price FROM products ORDER BY price DESC LIMIT 3;
```

> 示例数据仅用于跑通链路，**上线前务必用真实价目覆盖**，否则客服报的还是错价。
