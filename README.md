# 基于 Dify 工作流的智能客服助手与用户情感分析系统

一套跑在本地机房里的家电客服系统：用户关注微信公众号发消息 → 5 秒内收到基于企业知识库的答复 → 每次问答自动落库 → 事后对 8.4 万条历史会话做清洗、主题建模、情感分析与可视化大屏。

全程不依赖公网大模型，模型推理、工作流编排、数据存储都在内网完成。

> 人工智能综合实训 · 项目二

### 🌐 在线演示

**不开本地环境也能看效果** → https://ljx-001-00.github.io/dify-chatbot-data-analysis/

ECharts 大屏的纯静态版（1920×1080，自适应缩放），数据来自真实的 22,575 条会话分析结果。源码在 `docs/`，由 `08_智能客服数据大屏/dashboard/export_static.py` 生成。

## 系统怎么跑通的

```
微信用户
   │  发消息
   ▼
微信公众号服务器
   │  转发（经 frp 内网穿透）
   ▼
┌──────────────────────────────────────┐
│ P1 · Windows 业务主机                 │
│  wechat_public_bot.py  Flask :80      │  ← 签名校验 / AES 解密
│    ├─ 价格类问题 → price_router.py    │     结构化查询，杜绝编造价格
│    └─ 其余      → Dify 工作流 API     │
│  MySQL MCP Server      :8095/mcp      │  ← 把 SQL 执行包装成工具
└──────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────┐
│ P2 · openEuler 智能中枢               │
│  Dify 1.8.0（11 容器）  工作流编排     │
│  Xinference 9997        CPU 推理      │
│  MySQL 8.0             问答落库       │
└──────────────────────────────────────┘
   │
   ▼  数据沉淀后离线分析
22,575 条有效会话 → 清洗 / LDA / 情感 → 7 份 CSV → ECharts 大屏
```

## 快速开始

### 只看效果：本地大屏（无需数据库、无需联网）

```bat
cd 08_智能客服数据大屏
双击 启动大屏.cmd
:: 或 python dashboard\app.py  → 浏览器打开 http://127.0.0.1:5001
```

大屏读的是 `data_analysis\datacube_export\*.csv`，数据已随仓库附带，可直接演示。

### 跑数据分析流水线（需要 MySQL）

```bat
cd 08_智能客服数据大屏
pip install -r requirements.txt
python data_analysis\run_all.py
```

数据库连接见 `data_analysis\cfg.py`，可用 `MYSQL_HOST` / `MYSQL_USER` / `MYSQL_PASSWORD` 环境变量覆盖。

### 接微信公众号（需要自己的公众号 + 公网入口）

```bat

pip install flask requests wechatpy pymysql
:: 按下方「需要自己填的配置」设置环境变量后
python wechat_public_bot.py
```

## ⚠️ 需要自己填的配置

本仓库**已做脱敏**：所有真实密钥、公众号凭据、公网与内网 IP 均已替换为占位符，代码改为从环境变量读取。复现时必须自行填写：

| 环境变量 | 说明 | 代码中的默认值 |
| --- | --- | --- |
| `WECHAT_APP_ID` | 公众号 AppID | `<YOUR_APP_ID>` |
| `WECHAT_VERIFY_TOKEN` | 公众号后台「消息推送」里自己填的 Token，两边必须一致 | `<YOUR_VERIFY_TOKEN>` |
| `WECHAT_AES_KEY` | 安全模式必填，43 位 EncodingAESKey；明文模式留空 | 空 |
| `DIFY_API_KEY` | Dify 应用 → 访问 API → API 密钥 | `<YOUR_DIFY_APP_KEY>` |
| `DIFY_KEEPALIVE_KEY` | 保活工作流密钥（可选，用于压住 MCP 插件卸载延迟） | 空 |
| `DIFY_WORKFLOW_URL` | Dify 工作流端点 | `http://192.168.1.10/v1/workflows/run` |
| `MYSQL_HOST` / `MYSQL_USER` / `MYSQL_PASSWORD` | 问答落库与商品库 | `192.168.1.10` / `root` / `<MYSQL_PASSWORD>` |

`07_部署与配置/frpc.toml` 中的 `serverAddr` 与 `auth.token` 同样是占位符（`203.0.113.10` / `<FRP_AUTH_TOKEN>`），内网穿透需填自己的 frps 服务器地址与令牌。文档中的 `192.168.1.10` / `192.168.1.11` / `203.0.113.10` 均为示例地址。

参考 `.env.example` 批量配置。

## 两个值得说的技术取舍

**1. 价格类问题不走模型。** 模型编造价格在电商客服里是致命错误。`price_router.py` 先用正则识别价格/型号/参数类问题，直接查 `products` 表返回结构化结果，只有闲聊与政策类问题才进 Dify 工作流。

**2. 微信 5 秒硬超时 vs MCP 插件冷启动。** Dify 的 MCP 插件闲置约 15 秒会被卸载，下次调用要重新加载 4.5 秒，叠加推理就撞上微信超时。解法是一个只含「开始 → MCP list_tables → 结束」的轻量保活工作流，每 10 秒打一次，让插件常驻热态。落库则走后台线程，不占回复预算。

## 数据说明

`04_数据集与图表/分析中间数据/` 中的语料字段仅为 `time / text / src / text_len`（含情感分析结果），**不含昵称、手机号、订单号等任何用户标识**，可安全公开。原始数据来源为公开电商客服对话数据集。
