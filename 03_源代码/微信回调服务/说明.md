# 微信回调服务

## 文件 | File | 作用 |
|---|---|
| `wechat_public_bot.py` | 主程序，Flask 监听 80 |
| `start_bot.cmd` | 双击启动（已写入启动文件夹） |
| `frp_tunnel.cmd` / `run_frpc.cmd` / `start_frpc.cmd` | 启动 frp 隧道 |

## 请求处理流程

```
微信服务器 POST /wechat
  → 校验 signature（sha1(sort(token,timestamp,nonce))）
  → encrypt_type == 'aes' 则 WeChatCrypto 解密
  → 解析 XML 取 Content / FromUserName
  → 敏感词拦截（命中则回固定话术，不进模型）
  → POST Dify /v1/workflows/run（response_mode=blocking，超时 1.5/4.8s）
  → 组装回复 XML（安全模式需加密）
  → 后台线程 save_history() 直连 MySQL 落库
  → 返回 XML
```

## 关键设计

| 设计 | 原因 |
|---|---|
| `DIFY_TIMEOUT = (1.5, 4.8)` | 微信硬超时 5 秒，留 0.2 秒给网络返回 |
| 启动时预热线程 | 首次请求 20.67 秒（worker 冷启动），预热后中位数 1.65 秒 |
| 落库走后台线程直连 MySQL | Dify 调 MCP 偶发 4.5 秒尖峰，实测会顶穿预算；MCP 自身只要 7 毫秒 |
| 敏感词三级拦截 | 辱骂类直接回统一话术，避免模型被诱导输出不当内容 |
| 超时返回兜底话术 | 宁可回「稍等，我马上回复您」也不让用户等到 5 秒无响应 |

## 多轮上下文（指代消解 + 短历史）

微信每条消息都是独立的被动回复，Dify 侧是工作流（无会话变量），所以上下文记忆放在本服务里，只做两件轻量的事：

| 机制 | 触发条件 | 效果 |
|---|---|---|
| **指代消解** | 本句含「它 / 这款 / 那款 / 该款 / 这个 / 那个」，且本句没有型号 | 用上一轮出现过的型号替换代词：`那它保修几年` → `那R40-A0保修几年` |
| **短历史前置** | 本句 ≤14 字或含追问词，**且**本句没有型号 | 前面加一句 ≤95 字摘要：`（上一轮 用户：…｜助手：…）\n还有别的型号吗` |

设计取舍：

- **不无脑拼历史**。独立长问题（如「X50-B2 和 R60-A1 能耗区别」）原样发出，避免历史把知识检索带偏。
- **指代消解优先于拼历史**。型号补全后 query 本身已自包含，检索更准、token 更省。
- **只在内存**，每个用户最多 2 轮、最多 500 个用户，进程重启即清空。
- 只记录模型真实回答，兜底话术和敏感词拦截不入历史。

实测（2026-10-23）：

```
[1] R40-A0多少钱        -> R40-A0参考价999元…            2.00s
[2] 那它保修几年         -> 实际发送「那R40-A0保修几年」
                        -> R40-A0的蓝钻搪瓷内胆保修8年…   1.73s
```

未接入历史前，第 2 句会反问「您指的是哪款产品」。

## 价格结构化查询（route: 不经过模型）

价格漂移的实测证据：同一句「我要最贵的」连问三次、不带任何历史，得到三个答案
（16HD8/5999、16HG2/3999、16HG2/4999），两次同型号不同价。原因是「最贵的」属于
**全局排序**问题，而 RAG 只给 TopK=4 段局部文本，模型没有全表，只能从眼前几段里挑一个数字。

解法：把价格、排名、型号参数类问题从检索里拿出来，直接查 MySQL。

```
微信消息
  → 敏感词拦截
  → price_router.answer_price_question()   ← 命中就直答（约 50 ms，结果恒定）
  → 未命中 → build_query() 指代消解 + 短历史 → Dify 工作流（RAG）
```

| 意图 | 判定 | SQL |
|---|---|---|
| 最贵 / 最便宜 | `最贵\|最高价\|最便宜\|最低价` | `ORDER BY price DESC/ASC LIMIT 2` |
| 单型号问价 | 型号正则命中 + 价格词 | `WHERE model=?` |
| 型号对比 | ≥2 个型号 + `对比\|区别\|哪个好` | `WHERE model IN (...)` |
| 按容量问价 | `(\d{2,3})\s*(升\|L)` + 价格词 | `WHERE capacity_l=?` |
| 全部型号 | `有哪些型号\|推荐几款` | `ORDER BY price ASC LIMIT 8` |

接入后同一问题连问三次，回答**逐字一致**、耗时 50 ms（原来 1.7~2.2 s 且每次都变）。
非价格问题（如「漏水怎么办」）返回 `None`，照旧走 Dify，行为不变。

数据维护：`07_部署与配置/products.sql` 建表 + 示例数据；
真实价目用 `python init_products.py 价目表.csv` 覆盖（CSV 支持中文表头，价格填整数）。
